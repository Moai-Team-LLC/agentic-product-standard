# APS-2026-01 — MCP specification 2026-07-28

- **Status:** Informative advisory, issued with Standard v3.3.1 (2026-09-27). The normative treatment is Definition of Done item 26 in Standard v4.0.
- **Revised** with v4.0.0-rc.1 after a review against the specification sources: the deprecation timeline (Dynamic Client Registration added; HTTP+SSE on a shorter clock), the `private` cache scope, which credentials are bound to an issuer, and the gateway's header duty are corrected, and MCP Apps is no longer listed as moved (it was always an extension).
- **Affects:** Part II · Layer 2 (tool integration — MCP by default), Part II · Layer 8 (Security & Identity), DoD 14, anti-pattern 15, and the `tool-design-mcp` skill.
- **Numbering:** written against v3.3.1. In v4.0, `STANDARD.md` Part II sections are called **Stack 1–9** and "Layer N" means a harness layer only ([ADR-0005](../adr/0005-layer-and-stack-numbering.md)): read "Part II · Layer 2 / 5 / 8" below as Stack 2 / 5 / 8.
- **Primary sources:** [the 2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28) and [its changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); the [release post](https://blog.modelcontextprotocol.io/posts/2026-07-28/) (28 Jul 2026).

## Why this advisory exists

Standard v3.3 tells you to target MCP **2025-11-25** and to "branch for the 2026-07-28 release candidate." That release candidate was locked on 21 May 2026 and published as final on **28 July 2026**. The four Tier-1 SDKs (TypeScript, Python, Go, C#) supported it on release day, and Rust supported it in beta. The Layer 8 controls in v3.3 are still correct. They were written for the 2025 transport and auth model, though, and several of their assumptions changed. This note says which ones, and what to do before v4.0 makes it normative.

## What changed that the standard cares about

| Change (spec reference) | What it means for a v3.3 product |
|---|---|
| **Stateless core.** Protocol-level sessions and the `Mcp-Session-Id` header are removed (SEP-2567); `initialize` is removed, and the protocol version and capabilities travel in each request's `_meta` (SEP-2575). Servers that need state across calls mint explicit handles. | State kept in the transport session is now state nobody can see. Move it into explicit, server-minted handles or your own store. This is DoD 2 (*state externalized*) applied to the protocol. |
| **Multi round-trip requests** replace server-initiated requests such as `elicitation/create`, `sampling/createMessage` and `roots/list` (SEP-2322). The server returns `input_required`; the client retries with the answers and echoes an opaque `requestState`. | Human-in-the-loop through elicitation now arrives as an `input_required` result, which fits the durable-pause pattern (Part II · Layer 5). The spec says servers **MUST** treat `requestState` as attacker-controlled input, and **MUST** integrity-protect it (e.g. HMAC or AEAD) when it influences authorization, resource access, or business logic — rejecting state that fails verification. |
| **Routing headers.** `Mcp-Method` is sent on every request, and `Mcp-Name` on `tools/call`, `resources/read` and `prompts/get`, so that gateways can route and inspect traffic without parsing the body. Servers **MUST** reject a header that disagrees with the body (SEP-2243). | A gateway can now authorize per tool at the edge, which gives Layer 8 an enforcement point outside the model. Gateways that enforce policy on these headers **SHOULD** reject requests whose `MCP-Protocol-Version` is older or absent, because those servers do not check the headers against the body. |
| **Caching hints.** List and read results carry `ttlMs` and `cacheScope` (`public` or `private`); caches of `private` results **MUST NOT** be shared across authorization contexts — a different access token requires a different cache (SEP-2549). | Re-verify the tool-definition hash pin (DoD 14) on every refetch, not only at install. In any shared cache, key `private` entries by authorization context; a tenant boundary alone is not enough. The same leak path applies to tenant isolation. |
| **Authorization hardening.** Dynamic Client Registration is deprecated in favour of **Client ID Metadata Documents**. Clients **MUST** validate a present `iss` against the recorded issuer before redeeming a code (RFC 9207, SEP-2468). Clients that use pre-registered client credentials, or persist ones obtained through Dynamic Client Registration, **MUST** bind them to the issuing authorization server and never reuse them with another; Client ID Metadata Document IDs are portable. An **enterprise-managed authorization** extension exists (SEP-990). The server **MUST NOT** pass through the token it received from the client, as before. | Anti-pattern 15 grows a variant: a client that can only register through DCR. New clients use a Client ID Metadata Document where the authorization server supports one, or pre-registration; keep DCR as a fallback only. Validate `iss`. Bind stored client credentials to their issuer. |
| **Deprecations.** Roots, Sampling and Logging are deprecated (SEP-2577), and so is Dynamic Client Registration. Deprecated features get a minimum 12-month window, so these four become eligible for removal no earlier than the first revision released on or after **28 Jul 2027**; the window can shrink to 90 days for an active security risk (SEP-2596). The legacy HTTP+SSE transport, deprecated since 2025-03-26, was given only a three-month grace period once SEP-2596 was final, so it may go in the next revision. Separately, Tasks move from the core into the `io.modelcontextprotocol/tasks` extension (SEP-2663) — a move, not a deprecation. | Take no new dependencies on deprecated features. Put a sunset date on existing ones — for HTTP+SSE, now. |
| **Official conformance suite:** [`modelcontextprotocol/conformance`](https://github.com/modelcontextprotocol/conformance). | Run it in CI against your server and your client. As of this advisory, the `latest` npm tag (0.1.16) predates 2026-07-28 support, so pin the pre-release that provides `--requirements 2026-07-28` (0.2.0-alpha.11 when this was written). |

## What to do now

- [ ] Inventory every MCP connection: which side you own (client or server), the protocol revision it speaks, and a sunset date for anything still on 2025-11-25.
- [ ] Remove any dependence on `Mcp-Session-Id`. Carry cross-call state as explicit handles or in your own store.
- [ ] Treat `requestState` as untrusted input; integrity-protect and verify it wherever it influences authorization, resource access, or business logic.
- [ ] Re-verify pinned tool-definition hashes whenever a cached `tools/list` expires. Never serve a `private` cache entry outside the authorization context it was fetched under.
- [ ] New clients use a Client ID Metadata Document or pre-registration (DCR only as a fallback), validate `iss`, and bind stored client credentials to their issuer. Token passthrough stays forbidden.
- [ ] Build no new features on Roots, Sampling, or Logging.
- [ ] Add the official conformance suite to CI at a pinned version.
- [ ] If an MCP gateway fronts your servers, authorize on `Mcp-Method` and `Mcp-Name`, and reject requests whose `MCP-Protocol-Version` is absent or predates header validation; the servers behind it reject header/body mismatches.

v4.0 turns this checklist into DoD item 26 (*MCP protocol & auth baseline*).
